# Changelog

All notable changes to this project are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and
the project aims to follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Two things are versioned separately and matter more than the package version to
anyone consuming output: the **on-disk schema versions** (truth, estate,
observed, prediction, evaluation, comparison, bundle, DataHub round-trip,
OpenMetadata mapping coverage, OpenMetadata round-trip) and
the **generator versions**. A
change to either alters generated bytes, so it is called out explicitly in the
entries below.

## [Unreleased]

### Added

- **First verified OpenMetadata compatibility point: `1.13.3`.**
  `VERIFIED_OPENMETADATA_VERSION` moves `None` → `"1.13.3"`, earned by canary run
  `31528890425` against a pinned, throwaway server
  (`server@sha256:997d666b01f674fc4d587f034759c826082ea7666cd7bc0e6db8fdbb707df010`,
  self-reporting revision `255f6694913b84797064a42859cda3f2a3425dc6`): 830/830
  entities retrieved and matched, completeness, fidelity, containment and
  non-leakage all green, **0** discrepancies, **0** leak findings, 19 live tests
  including the negative controls that prove a clean result is not a comparison of
  nothing against nothing. Normalization contract v2.

  **A tested point, never a range.** No other release is claimed, including other
  `1.13.x` patches; `OPENMETADATA_MODEL_TARGET_RANGE` remains a declared target for
  the payload shape and is not evidence.

  **Scope: observed mode.** What ran end to end was `bundle → export-openmetadata
  --mode observed → ingest-openmetadata → real OpenMetadata 1.13.3 → readback →
  round-trip verification → negative controls`. **Truth mode has not been run
  against a real server** and continues to rest on the deterministic offline
  contract and the vendored schemas. The canary does prove that an *observed*
  ingestion leaves no `dataswampTruth*` property and no privileged tag in a real
  catalogue — that is non-leakage, not truth-mode verification. The export
  manifest states which of the two an export carries, per mode, so a stored truth
  export cannot quote an observed export's evidence.

  No report schema field was added for this: `OM_ROUNDTRIP_SCHEMA_VERSION` stays
  `1`, `OM_ADAPTER_VERSION` stays `1.1.0`, and no deterministic plan fixture,
  golden digest or DataHub artefact moves. Emitted export *manifests* do change,
  because they record the constant.

### Changed

- **OpenMetadata normalization is at version 2, on real-server evidence.**
  `OM_NORMALIZATION_VERSION` moves `1` → `2`, which changes the
  `normalization_version` recorded in every `roundtrip-report.json`. The first
  live 1.13.3 canary produced 913 discrepancies, classified before anything was
  changed. **The version moved for the 830 server-materialized ones alone**; the
  counter tracks forgiveness, and the description behaviour below forgives
  nothing.

  *Materialized defaults* (830 of them, verdict **B**). OpenMetadata answers an omitted optional
  field with an empty relationship set or the default its own schema declares —
  `owners: []`, `provider: user`, `isJoinable: true`, `autoClassificationPriority:
  50`. Forgiveness is doubly conditional: the plan must have omitted the field
  *and* the retrieved value must equal the declared default exactly, so
  `owners: [someone]` on an entity DataSwamp gave no owner is still a containment
  discrepancy. Each path is scoped to the entity types whose `Create` schema
  actually accepts it, and a mechanical test asserts this list and the
  platform-generated list stay disjoint.

  Seven fields also joined the platform-generated list under the existing
  create-schema exclusion standard: `entityStatus`, `followers`, `lifecycleStage`,
  `childrenCount`, `userCount`, `deprecated` and `disabled`. `entityStatus` had
  been *deliberately excluded* in v1 on an offline assumption — that only a PATCH
  sets it. The canary showed the server writing it on create, on 799 entities
  nobody patched, and pinned schema evidence was then vendored behind it: live
  evidence superseded an unverified assumption, which is not the same thing as a
  red check justifying forgiveness. `retentionPeriod`, `sampleData` and
  `certification` remain excluded.

  Four upstream entity schemas (`tag`, `classification`, `glossary`,
  `glossaryTerm`) are now vendored at the same pinned commit, because a
  forgiveness rule is only mechanically checkable where both halves of the
  create/entity pair are present. No compatibility point is claimed:
  `VERIFIED_OPENMETADATA_VERSION` stays `None` until a canary runs completely
  green.

- **Round-trip comparison is documented as two explicit stages.** The guardrail
  is unchanged and unqualified — *a DataSwamp-sent semantic value is never a
  normalization-forgiveness candidate* — and the code, the emitted contract and
  `docs/openmetadata.md` now name the two stages it separates. Stage 1 relates two
  encodings of the same sent value (reference projection, unordered relationship
  lists) where the transformation is exact and invertible; stage 2 is forgiveness
  of server-owned state, and `OM_NORMALIZATION_VERSION` counts stage 2 alone.

### Added

- **Stage-1 reconciliation of OpenMetadata's server-side HTML escaping.** The
  remaining 83 discrepancies from the first live canary: OpenMetadata escapes
  markup-significant characters in `description` on write, so `study 'x'` returns
  as `study &#39;x&#39;`. This **forgives nothing and did not move
  `OM_NORMALIZATION_VERSION`** — the description is still compared in full, and
  only its two encodings are related. Admitted only where the inversion is
  provably unambiguous: the sent text must carry no HTML entity of its own, so
  exactly one decoding round can relate the two strings, and decoding the readback
  must then reproduce the sent text character for character. A truncation, a
  rewrite, a double-encoded readback or an escaped `displayName` all still fail
  fidelity.

- **Optional live OpenMetadata canary.**
  `.github/workflows/live-openmetadata.yml` stands up a real, pinned, throwaway
  OpenMetadata `1.13.3` and runs the whole product path through it —
  `demo` → `ingest-openmetadata --dry-run` → start → `ingest-openmetadata --yes`
  → `verify-om-ingestion` → a live pytest suite. It is optional and
  non-blocking: `workflow_dispatch`, a weekly schedule, and pull requests
  carrying the `live-openmetadata` label. There is no `push` trigger and it is
  never a required check. Closes
  [#39](https://github.com/ronfinn/dataswamp-biosystems/issues/39).

  The deployment is upstream's own quickstart compose at
  `255f6694913b84797064a42859cda3f2a3425dc6` — the same commit the vendored
  schemas came from — sanitized by
  `scripts/render_live_openmetadata_compose.py` rather than reimplemented: fixed
  container names, the `./docker-volume/db-data` host bind mount and the
  hardcoded subnet are removed, the Airflow service the server does not depend
  on is dropped, and only `8585`/`8586` reach the host. The renderer is total —
  an upstream change that removes something it expects to sanitize is a render
  failure to read, not a quietly weaker deployment.

  Authorization uses OpenMetadata's own `NoopAuthorizer`/`NoopFilter`, selected
  through variables the pinned `conf/openmetadata.yaml` already interpolates, so
  the job needs **no repository secret and no token**: `OPENMETADATA_JWT_TOKEN`
  is never set.

  A new `live_openmetadata` pytest marker carries the real-server suite, and is
  deselected by default alongside `live`. The suite skips with a clear reason
  when `OPENMETADATA_HOST_PORT` is unset and never falls back to a local guess.
  It asserts the four claims independently, per-family materialization for every
  supported entity family, the corrected DataProduct identity and asset
  attachments from #37, and three load-bearing negative controls — a withheld
  entity must be reported as an extra, a mutated expectation must be reported
  against the real readback, and a deliberately foreign entity must *not* be
  accused of being a DataSwamp extra — so that an empty or broken readback can
  never produce a green canary.

  No version constant moved. `VERIFIED_OPENMETADATA_VERSION` remains `None`:
  implementing a canary is not running one, and only a completely green
  real-server run can set it.

### Fixed

- **OpenMetadata DataProduct identity and asset-attachment transport.** One
  defect across four surfaces, found while confirming what looked like an inert
  endpoint-annotation typo. Closes
  [#37](https://github.com/ronfinn/dataswamp-biosystems/issues/37).

  OpenMetadata derives a DataProduct's `fullyQualifiedName` from its `name`
  alone — `DataProductRepository` does not override the root-level default, and
  the owning Domain is a field rather than a path component. The adapter declared
  `dataswamp-<programme>.<product>` while sending `name: <product>`, so a real
  catalogue would have created the unnamespaced `<product>`: every FQN-addressed
  read and write named an entity no server had. The identity is now the single
  root-level segment `dataswamp-<encoded programme>~~<encoded product>`, with the
  two ids encoded *separately* — joining first and encoding after is not
  injective, because the codec escapes a separator inside an id and the joining
  one identically.

  The live client sent `PUT /api/v1/dataProducts/name/{fqn}/assets/add`, which
  `DataProductResource` does not declare in any form; the write is
  `/{fqn}/assets/add`, and only the *read* uses `/name/{fqn}/assets`. The emitted
  `ENDPOINTS["dataProductAssets"]` annotation named a third path again, and is now
  correct and pinned against the client's route by a test.

  None of it was caught offline because `fake_om.py` agreed with the client on
  all three points — it derived a DataProduct FQN as `domain.name`, matched
  `/name/{fqn}` plus any tail, and stored only the forward half of an attachment.
  It now derives every FQN from upstream's `quoteName(name)`, enumerates the two
  asset routes separately, and materializes the reverse `dataProducts` edge that
  `bulkAddAssets` creates. A test asserts it imports nothing from `client.py`.

  A container's `dataProducts` is therefore compared as expected readback state
  derived from the plan's own attachments, not forgiven:
  `OM_NORMALIZATION_VERSION` stays `1` and `OM_ROUNDTRIP_SCHEMA_VERSION` stays
  `1`. `VERIFIED_OPENMETADATA_VERSION` stays `None` — this was proved from pinned
  source, and no server has been run.

  **`OM_ADAPTER_VERSION` moves `1.0.0` → `1.1.0`**: emitted DataProduct identity
  changes, so a consumer holding an FQN from a `1.0.0` export cannot match one
  emitted now. Only the two `data-product` and `data-product-assets` records in
  the committed OpenMetadata entity fixtures move; mapping coverage, lineage,
  test results, custom properties, the DataHub fixtures and the benchmark golden
  digests are byte-identical.

  Also fixed while proving the 256-character bound: `encode_id` checked only the
  *encoded segment*, leaving every root-level identity's `dataswamp-` prefix
  unaccounted for. The bound now applies to the emitted name.

### Added

- **OpenMetadata live ingestion and round-trip validation, offline-testable.**
  `dataswamp ingest-openmetadata --export-dir <dir> [--dry-run] [--yes]` replays an
  emitted OpenMetadata export into a running catalogue, and `dataswamp
  verify-om-ingestion --export-dir <dir> --output-dir <dir>` reads the catalogue
  back and reports **four independent claims** — completeness, fidelity,
  containment, and observed-mode non-leakage — rather than one opaque verdict.
  Closes [#35](https://github.com/ronfinn/dataswamp-biosystems/issues/35). See
  [docs/openmetadata.md](docs/openmetadata.md).

  The path is strictly downstream of the emitted export: `bundle →
  export-openmetadata → emitted export → ingest-openmetadata →
  verify-om-ingestion`. The live commands consume the export directory and
  nothing else — no bundle, no generator, no truth shard, no defect ledger, no
  control partition, no rule scope, no expected finding, no scenario, no
  evaluation output — which is enforced structurally in
  `tests/adapters/test_isolation.py`, because verifying an *observed* export must
  need no privilege.

  `client.py` is the only module that opens a socket and the only one that names
  an endpoint, a verb or an authorization header. Standard library only: no
  `openmetadata-ingestion`, no `requests`, no `httpx`, no new dependency of any
  kind. Credentials come from `OPENMETADATA_HOST_PORT` and `OPENMETADATA_JWT_TOKEN`
  and from nowhere else — never a CLI argument, and never present in a `repr`, an
  exception, a log, a report or a recorded URL. `--dry-run` performs **zero**
  network activity, including no health check, proved by poisoning
  `socket.socket`, `socket.create_connection` and `urllib.request.urlopen` rather
  than by mocking the client.

  Replay order is load-bearing and is preserved exactly: a container needs its
  parent, an `extension` key needs its custom property registered, a lineage edge
  needs both endpoints. Nothing sorts, groups, batches or parallelises the plan.
  Three writes need a server-assigned UUID because OpenMetadata keys an
  `EntityReference` by `id` — custom-property registration, data-product asset
  attachment and lineage — and the emitted plan already declares each of those
  targets as a `Reference` block for exactly that reason; the transport resolves
  them by FQN and changes nothing else. A resolved UUID never becomes DataSwamp
  identity.

  Containment coverage is **declared per entity family**, not claimed uniformly:
  `provable` where a server-side scope filter makes ownership structural
  (Containers via `?service=`, Tags via `?parent=`), `namespace-prefix` where it
  rests on DataSwamp's reserved FQN prefix, `unavailable` where nothing was
  enumerated. An entity outside every ownership rule is somebody else's and is
  never reported as a DataSwamp extra.

  **New schema versions, both owned entirely by this feature and both independent
  of DataHub's:** `OM_NORMALIZATION_VERSION = 1` and
  `OM_ROUNDTRIP_SCHEMA_VERSION = 1`. Normalization v1 is deliberately minimal and
  its evidence standard is mechanical: a field is forgiven only where
  OpenMetadata's own `Create<Entity>` schema sets `additionalProperties: false`
  and omits it while the entity schema declares it, proving DataSwamp cannot have
  sent it. Forgiveness is additive-only — a value DataSwamp sent is always
  compared — and every rule has a paired test proving an adjacent field is still
  caught. `retentionPeriod`, `sampleData`, `certification` and `entityStatus` are
  deliberately *not* forgiven: OpenMetadata does not generate them, so a value
  there is somebody else writing to DataSwamp's entities.

  Tests run against a **strict fake OpenMetadata server** built to disagree with
  the client. It imports nothing from `client.py`; routes are written out again
  from upstream's resource classes and request bodies are validated against the
  vendored upstream JSON schemas. It rejects the wrong method, an unknown path, a
  malformed envelope, a missing or unknown field, an unregistered `extension` key,
  a forward reference and a bare property-type name, and it withholds opt-in
  `fields` that were not requested. This is a direct response to the DataHub fake
  once accepting the wrong wire dialect for months because it modelled the client
  instead of the API.

  Quality checks remain **unsupported natively**, unchanged from #33. No Table,
  Column, Database, DatabaseSchema, TestDefinition, TestSuite or TestCase is
  fabricated to unlock them; `TestDefinition.entityType` admits only `TABLE` and
  `COLUMN` while DataSwamp datasets are Containers, and asserting table scope for a
  Container is the same fabrication one level removed.

### Unchanged, deliberately

- `OM_ADAPTER_VERSION` stays `1.0.0` and the emitted OpenMetadata export bytes are
  unchanged; the #33 fixtures, the DataHub fixtures and the golden digests are all
  byte-identical.
- `VERIFIED_OPENMETADATA_VERSION` **remains `None`.** Every offline test passes and
  that changes nothing: the request shapes were read from upstream source and
  proved against a fake, and neither is evidence about a running server. A green
  fake is not a green server. Only a pinned real-server canary earns a
  compatibility point, per
  [ADR 0006](docs/adr/0006-compatibility-points-not-ranges.md).
- `OPENMETADATA_SCHEMA_TARGET` stays `1.13.3-release` and DataHub's versions,
  normalization contract and verified version are untouched.

  One discrepancy was found and deliberately *not* fixed here: the emitted
  `endpoint` annotation on `data-product-assets` records reads
  `/api/v1/dataProducts/assets/add`, while the real endpoint is
  `/api/v1/dataProducts/name/{fqn}/assets/add`. The annotation is inert
  documentation — `client.py` owns the paths and never reads it — so the live path
  is unaffected. Correcting it would move the #33 fixtures and is a separate,
  deliberate change rather than a silent repair inside this one.

### Added

- **A deterministic OpenMetadata mapping and export.** `dataswamp
  export-openmetadata --bundle <dir> --mode observed|truth` emits an ordered,
  load-order-aware plan against OpenMetadata's **native** model: whole-entity
  `Create<Entity>` requests, hierarchical `fullyQualifiedName` identity, a
  `CustomStorage` StorageService over a study → dataset → file Container
  hierarchy, plus Domains, Data Products, Teams, Glossaries, a Classification and
  dataset lineage. Emitted as `custom-properties.jsonl`, `entities.jsonl`,
  `lineage.jsonl`, `test-results.jsonl`, `mapping-coverage.json`,
  `export-manifest.json` and `provenance.json`, byte-identical for identical
  input. Closes
  [#33](https://github.com/ronfinn/dataswamp-biosystems/issues/33). See
  [docs/openmetadata.md](docs/openmetadata.md).

  It is deliberately **not** a copy of the DataHub adapter's entity/aspect
  architecture, and no `adapters/common/` is created: with two adapters it is now
  possible to judge what is genuinely common rather than merely similar.

  Three mapping decisions are load-bearing. Datasets become **Containers, not
  Tables** — DataSwamp holds no honest relational column metadata, so no Table,
  column, database or field-level schema is invented. Stewardship is preserved
  *separately* from ownership and classified **lossy**, because OpenMetadata
  draws no owner/steward distinction and its `experts` field takes user login
  names rather than teams. Quality checks are classified **unsupported**, because
  `TestDefinition.entityType` admits only `TABLE` and `COLUMN` and emitting one
  for a Container would fabricate applicability; the check facts survive as
  custom properties and the results as an explicitly blocked plan.

  **No live OpenMetadata compatibility is claimed.** There is no ingestion
  command, no client, no network and no canary; nothing has ever been loaded into
  a running instance. `VERIFIED_OPENMETADATA_VERSION` is `None` and every emitted
  manifest says so. The declared `>=1.9,<2` model range is a *target* for the
  payload shape, not tested evidence — reading a schema is not running against a
  server, per [ADR 0006](docs/adr/0006-compatibility-points-not-ranges.md).
  `OM_NORMALIZATION_VERSION` is deliberately not introduced: normalization is a
  round-trip concern and belongs to a later milestone.

- **A first-class mapping-coverage contract.** `mapping-coverage.json` ships in
  every OpenMetadata export and reports, per DataSwamp concept, a semantic
  classification (`exact` / `reasonable` / `lossy` / `unsupported`) *and*, as a
  separate axis, an operational state (`materialized_in_entity_export` /
  `deferred_live_write` / `deliberately_not_mapped`), with source, emitted and
  deliberately-dropped counts and a mandatory reason for anything not `exact`.
  Building a report that misses a declared concept or counts an undeclared one is
  an error, so a mapping change cannot start emitting something without
  classifying it. Versioned by `coverage_schema_version` (currently `1`).

- **Offline validation of OpenMetadata payloads against upstream's own schemas.**
  A minimum 21-file subset of `openmetadata-spec` is vendored under
  `tests/adapters/openmetadata/schemas/` from a recorded release and commit
  (`1.13.3-release`, `255f669`), with `additionalProperties: false` honoured so an
  unknown field fails rather than being silently dropped, and enum membership
  enforced. Refresh is deliberate — `scripts/update_openmetadata_fixtures.py
  --schemas|--fixtures --confirm --reason ...` — and `pytest` never rewrites the
  schemas or the fixtures. `jsonschema` is added as a **dev** dependency only.

- **[ADR 0007](docs/adr/0007-no-catalogue-client-dependency.md).** Generalises
  ADR 0005 from one integration to a policy: catalogue adapters emit documented
  payload shapes, validate them offline against upstream schemas where those are
  published, and take no catalogue-client runtime dependency. Worded as the
  *current* policy rather than an irreversible law — a future catalogue that can
  only be integrated responsibly through an official SDK should supersede this
  ADR rather than be worked around.

- **A live DataHub Quickstart canary, and the first tested compatibility point:
  DataHub `v1.7.0`.** The optional `live-datahub` workflow stands up a pinned
  Quickstart, runs the whole live path against it and requires zero
  discrepancies and zero leak findings. It is deliberately **not** a required
  check — weekly, `workflow_dispatch`, or a pull request labelled
  `live-datahub`. `VERIFIED_DATAHUB_VERSION` now names that release in every
  round-trip report's `live_support`. Closes
  [#28](https://github.com/ronfinn/dataswamp-biosystems/issues/28).
- **A drift-canary triage and compatibility policy.** A four-branch decision
  tree — DataSwamp bug, server-derived metadata, upstream DataHub change,
  infrastructure flake — with different permitted responses per branch, an
  explicit `DATAHUB_MODEL_VERSION` policy, and a procedure for recording a red
  weekly run. Normalization may never be widened merely because the canary is
  red. Closes
  [#29](https://github.com/ronfinn/dataswamp-biosystems/issues/29). See
  [ADR 0006](docs/adr/0006-compatibility-points-not-ranges.md) and
  [docs/datahub.md](docs/datahub.md#when-the-canary-goes-red).

- **DataHub live ingestion and round-trip validation.** `dataswamp
  ingest-datahub --export-dir <dir>` transmits an already-emitted DataHub export
  to a running catalogue, and `dataswamp verify-ingestion` reads the catalogue
  back and judges four claims *separately* — completeness, fidelity, containment
  and observed-mode non-leakage — writing `roundtrip-report.json`,
  `discrepancies.jsonl` and `leak-findings.jsonl`. Closes
  [#27](https://github.com/ronfinn/dataswamp-biosystems/issues/27). See
  [docs/datahub.md](docs/datahub.md).
- **No new dependency.** The GMS client is standard-library REST; `acryl-datahub`
  and every third-party HTTP client remain absent, and a test enforces it. Every
  endpoint path and every socket is confined to
  `adapters/datahub/client.py`. See
  [ADR 0005](docs/adr/0005-direct-rest-datahub-client.md).
- **A versioned normalization contract** governing what a round-trip forgives.
  Each rule carries a justification plus a paired test proving an adjacent
  non-ignored mutation is still caught, and unknown server additions default to
  visible differences. Shipped at `normalization_version` 1 with a single
  server-owned field; now at 2 — see below.
- **Conservative containment scope.** Extra-entity detection runs only for the
  five entity families whose URN namespace unambiguously identifies DataSwamp;
  the other four report coverage as *unavailable* rather than guessing. An
  unrelated catalogue entity is never reported as a DataSwamp extra.
- **Round-trip reports** with their own `roundtrip_schema_version` (1). No other
  schema moved, `ADAPTER_VERSION` is unchanged, no generated bytes moved, and
  the golden digests and DataHub export fixtures are untouched.

- **Benchmark run comparison and regression reports.** `dataswamp compare-runs
  --baseline <evaluation-dir> --candidate <evaluation-dir>` answers the question
  the evaluator cannot: *did my change help?* It differences two
  already-emitted evaluation directories and reports metric deltas, rule-level
  regressions, control-preservation regressions, per-tier and adversarial
  movement, and remediation changes. Closes
  [#17](https://github.com/ronfinn/dataswamp-biosystems/issues/17). See
  [docs/run-comparison.md](docs/run-comparison.md).
- **A new `comparison` layer** (`src/dataswamp_biosystems/comparison/`) with its
  own `comparison_schema_version` (1) and comparator version (1.0.0). No other
  layer's schema changed, no generated bytes moved, and the golden digests are
  unchanged.

### Fixed

- **DataHub live ingestion used the wrong API family.** Ingestion posted
  OpenAPI-dialect aspects (`{"aspect": {"json": ...}}`) to the rest.li
  `/aspects?action=ingestProposalBatch`, which deserializes an aspect as
  `GenericAspect` (`value` as serialized bytes plus `contentType`). A real GMS
  answered `HTTP 500 RequiredFieldNotPresentException`. The offline suite passed
  throughout, because the fake GMS accepted any request envelope. Live write,
  entity read, timeseries read and namespace enumeration are now **one API
  family end to end** (OpenAPI v3, `async=false`), and the fake GMS validates
  the request envelope so it can disagree with the client. Found by the #28
  canary on its first real run; **no emitted byte, mapping, fixture or schema
  changed.**

### Changed

- **`normalization_version` 1 → 2**, earned by evidence from the first live
  round-trip against DataHub v1.7.0: 4,398 discrepancies, of which **every one
  was the server adding derived metadata and none altered a value DataSwamp
  sent** (0 of 861 field-level differences). Two rule kinds were added, each
  with a justification and a paired test:
  - **Server-derived aspects**, exempt from *containment only* and never from
    fidelity — the entity's own key aspect (by rule, so `datasetKey` on a *tag*
    is still a finding), plus `browsePathsV2`, `aliases` and
    `dataPlatformInstance`.
  - **Server-added fields**, forgiven **only where DataSwamp sent no value** —
    `assertionInfo.entityUrn`, `domains.domainAssociations`,
    `ownership.ownerTypes`. A change to a value we *did* send is still a
    mutation, which is what makes this stricter than stripping the field.
- **The "transmitted verbatim" guarantee was wrong and has been replaced.** Live
  ingestion does not remap, synthesize, enrich or reinterpret emitted metadata;
  entity identity, entity type, aspect identity and semantic aspect content are
  preserved, and `client.py` alone encodes that content into the wire
  representation the DataHub API requires. The emitted `mcps.jsonl`/`mcps.json`
  remain the deterministic interchange artefacts and are never rewritten to suit
  a transport.

No other schema moved: `ADAPTER_VERSION`, `DATAHUB_MODEL_VERSION`,
`roundtrip_schema_version`, the golden digests and the committed DataHub export
fixtures are all unchanged.

### Notes on semantics

- **Read-only and downstream of the evaluation contract.** The comparison
  re-scores nothing, reads no prediction file, never opens the observed ground
  truth or the privileged scenario answer key, and writes nothing into either
  input directory. Every number it reports is the evaluator's own, differenced.
- **Incompatible runs are refused, not differenced.** Ground-truth fingerprint,
  profile, both seeds, the observed generator/schema versions, the evaluator and
  prediction schema versions, and the derived universe shape must all match. The
  error names every differing field with both values. There is no
  config-fingerprint check because the evaluator emits no such field, and this
  layer does not reach past the evaluation contract to recover it.
- **Undefined stays undefined.** If either side's metric is `null`, the delta is
  `null` and the direction is `undefined` — never `0.0`. Both numerators and
  denominators travel with every delta.
- **Direction is a field, not a sign.** Every metric and every error count
  carries an explicit `improved`/`regressed`/`unchanged`/`undefined` direction
  beside a `higher_is_better` flag; the raw delta stays `candidate - baseline`
  and is never sign-flipped to make "positive means better" true by
  construction.
- **Control preservation is first-class.** New and resolved control false
  positives are reported separately from reserved-control ones, as both a stock
  and a flow, so a candidate that buys recall by flagging clean entities cannot
  hide behind an improved F1. Because the evaluator emits no record for a clean
  unpredicted pair, the comparison joins on the *union* of emitted pairs and
  reconstructs the implicit true negative — an intersection join would drop
  exactly that regression.
- **Adversarial comparison is aggregate-only, and says so.** The evaluator does
  not tag individual pairs with scenario membership, so the payload carries
  `per_case_attribution_available: false` rather than implying an attribution it
  cannot support.
- **A regression does not fail the command.** It answers what changed; no
  threshold or CI gating is implied, and the summary carries
  `verdict_is_advisory: true`.

## [0.1.0] — 2026-08-07

**First official release.** It promotes `0.1.0rc1` unchanged in behaviour and
adds the work merged since it: the difficulty tiers, the adversarial scenario
engine, the reference baseline agents, and the generated-data licensing
decision. The whole benchmark workflow ships — generate a synthetic estate,
derive a defective observed view of it with a published answer key, score a
submission, package a portable bundle and export catalogue metadata — all
deterministic, offline and free of any real data.

The `0.1.0rc1` entry below describes the parts of that surface that were already
in place; this entry describes what changed after it. Nothing is claimed here
that the release does not do: there is no live catalogue ingestion, no LLM-backed
agent, no run-to-run comparison and no PyPI package.

### Added

- **Benchmark difficulty tiers.** Every one of the 41 defect rules is classified
  bronze, silver or gold by a declared per-rule **reasoning scope** — what
  evidence a detector must relate before it can decide — rather than by hand.
  Scopes are `single-record` (bronze, 13 rules), `cross-record` (silver, 15) and
  `cross-asset`/`peer-relative` (gold, 13). Difficulty is detection complexity
  and is independent of severity, of the maturity profile and of remediation
  availability; the independence is enforced by tests, not asserted. See
  [docs/difficulty-tiers.md](docs/difficulty-tiers.md).
- **Tier-restricted generation.** `dataswamp inject-defects --difficulty
  bronze|silver|gold|mixed`. `--profile` and `--difficulty` are independent
  filters that compose: the profile sets how many defects are injected, the tier
  sets which rules may inject them. A tier and profile with an empty
  intersection is an error rather than a silently empty benchmark.
- **Difficulty in the rule registry surface.** `list-defects` shows
  `[category/severity/difficulty]` per rule and a per-tier summary;
  `list-defects --json` gains a `difficulty_coverage` block; `validate-defects`
  fails if any rule is unclassified.
- **Per-tier evaluation.** `summary.findings.by_difficulty` (full confusion
  matrix, metrics, reserved-control false positives and rate, and remediation
  coverage/correctness/end-to-end/unsafe counts per tier),
  `summary.universe.rules_by_difficulty`, a new `difficulty-metrics.jsonl`
  alongside the existing rule and category metric files, and a **By difficulty**
  section in `evaluation-report.md`. Difficulty is derived from the rule
  registry, never duplicated into emitted ground truth.
- **Measured per-tier baseline results** for all three reference agents, pinned
  cell by cell in `tests/baselines/test_tier_scores.py` and published in
  [docs/difficulty-tiers.md](docs/difficulty-tiers.md) and
  [docs/baselines.md](docs/baselines.md).

### Changed

- **The generated benchmark data now has a designated licence.** The official
  generated datasets and bundles the project distributes, from v0.1.0 onward,
  are licensed **CC BY-NC 4.0** (SPDX `CC-BY-NC-4.0`): noncommercial research,
  education and AI/model/agent evaluation are permitted with attribution, and
  commercial use requires separate permission from the project owner. **The
  software remains MIT, unchanged.** The project makes no claim over data a
  third party generates independently by running the MIT-licensed software.
  Nothing distributed before v0.1.0 is retroactively relicensed. New root files
  `DATA-LICENSE.md` and `COMMERCIAL-LICENSING.md`; rationale in
  [ADR 0004](docs/adr/0004-generated-data-licensing.md), which supersedes and
  replaces the former open-decision document.

  Bundle manifests now declare `generated_data_license: CC-BY-NC-4.0` (was
  `not-separately-defined`) with the licence URL, starting release and
  commercial-permission note; every bundle ships a verbatim copy of
  `DATA-LICENSE.md`, and `verify-bundle` checks the licensing material.
  **`BUNDLE_SCHEMA_VERSION` is unchanged** — `licensing` is an open block and
  `generated_data_license` a free string, so this is not a schema change.
  **Bundle fingerprints change**, because bundle bytes changed; the truth,
  estate and observed layers are byte-identical and no golden digest moves.
- **Evaluation schema 1 → 2**, additively. Everything a schema-1 reader looked
  for is still in the same place with the same meaning; the tier blocks and the
  new metric file are new material.
- `validate-observed` now recovers the generated tier from `provenance.json`, so
  it regenerates the same benchmark it is checking.

### Added (adversarial scenarios)

- **The adversarial tier.** `dataswamp inject-defects --difficulty adversarial`
  switches to a **scenario engine** that *constructs* cases rather than sampling
  rules: it names its own targets, dresses reserved controls into near misses,
  and scopes each rule's population to the constructed neighbourhood. Six case
  classes, all required — `near-miss-control`, `cross-record-ambiguity`,
  `cross-asset-inconsistency`, `overlapping-evidence`, `no-remediation` and
  `decoy-candidate`. No ordinary defect is relabelled adversarial, and no rule
  holds `Difficulty.ADVERSARIAL`; a run that cannot construct a required case
  class fails naming it rather than emitting a partial tier. See
  [docs/adversarial-scenarios.md](docs/adversarial-scenarios.md).
- **Near-miss controls.** Clean entities deliberately made to *resemble* a
  defect, applied only to reserved controls and always landing one principled
  step on the valid side of the rule they mimic (equal sizes rather than
  inverted; a count of one rather than zero; a semver prerelease rather than a
  free-text token; restricted-and-internal rather than restricted-and-external).
- **`scenarios.jsonl` and `scenario-transformations.jsonl`**, emitted only by an
  adversarial run. Both are **privileged answer key**, named in
  `FORBIDDEN_INPUT_FILES` so no baseline can open one; there is deliberately no
  public scenario view. A `ScenarioTransformation` is deliberately *not* a
  `MutationRecord`: a near miss must never join to a defect instance, finding or
  remediation.
- **A separate near-miss control invariant.** Ordinary controls keep
  field-for-field truth equality, untouched. A near miss instead has to satisfy
  nine itemised clauses — reserved control, absent from every `selected_ids`,
  absent from the defect and mutation ledgers, every differing field declared,
  no undeclared field differing, before/after matching both graphs, and the
  emitted record still satisfying a *named executable predicate* re-run against
  the emitted bytes. Violations name the scenario, entity, field and clause.
- **Scenario coverage**, in a `scenarios` block of `profile-summary.json` present
  only for an adversarial run, including `uncovered_required_case_types` — a
  non-empty list fails generation.
- **Scenario-aware evaluation.** An `adversarial` block in
  `evaluation-summary.json` (always present, empty-but-shaped otherwise) and a
  `scenario-metrics.jsonl` for adversarial benchmarks: confusion matrix and
  metrics by case class, near-miss false-positive rate, wrong-entity and
  wrong-rule attributions, correct abstentions, unsafe remediations against near
  misses and correct explicit no-remediation decisions. No second scoring engine
  — it regroups pairs the one evaluator already scored, and the case-class counts
  sum to the tier's matrix.
- **Measured adversarial baseline results** for all three reference agents,
  pinned by hand in `tests/baselines/test_adversarial_scores.py` and published in
  [docs/adversarial-scenarios.md](docs/adversarial-scenarios.md) and
  [docs/baselines.md](docs/baselines.md). Reported as measured: the naive agent
  is fooled by a third of the lookalikes it can see, and two case classes have
  zero true positives across all three agents.

### Changed (adversarial scenarios)

- **Observed schema 3 → 4, observed generator 1.2.0 → 1.3.0**, additively. The
  two ledgers are optional and a schema-3 directory remains readable
  (`SUPPORTED_OBSERVED_SCHEMA_VERSIONS` is `{3, 4}`); no record that existed at
  schema 3 changed shape or meaning.
- `GroundTruth.known_entities` now includes collaterally-mutated entities. They
  are neither a control nor the target of a finding, so on a scenario-restricted
  benchmark a reasonable prediction about one would previously have been rejected
  as a broken submission rather than scored as an out-of-scope false positive.
- **Golden digests regenerated, deliberately and narrowly.** The only canonical
  bytes that moved are the `generator_version` and `schema_version` fields in
  observed `meta`, which appear in `observed-graph.json`, `profile-summary.json`
  and `summary.md`. Every ledger and the whole truth and estate output are
  byte-identical, so rule selection, control membership and ledger order did not
  move; every measured baseline score is unchanged, and only the recorded
  generator version and ground-truth fingerprint moved in the baseline fixture.

### Notes

- **`mixed` still means the ordinary rule catalogue** — bronze, silver and gold
  together — and never includes adversarial scenarios. Folding them in would
  change the default benchmark's bytes and every published score with them, so an
  all-tier mode, if ever wanted, has to be a new explicit selection.
- **The adversarial set is a focused initial six case classes** over a small
  constructed universe (19 scored pairs at the demo profile), not a model of
  real-world ambiguity. Limits are listed in
  [docs/adversarial-scenarios.md](docs/adversarial-scenarios.md#limitations).
- **Bronze/silver/gold, the prediction schema, the evaluation schema, the bundle
  layout and the DataHub export are unchanged.**

### Added (reference baseline agents)

- **Reference baseline agents.** Three small, readable benchmark participants
  published so a result has something to be compared against: `null` (claims
  nothing — the recall floor and specificity ceiling), `naive-metadata` (shallow
  single-field signals) and `rule-based` (20 of the 41 defect rules
  re-implemented against observed metadata). New commands `dataswamp
  run-baseline` and `dataswamp list-baselines`; `run-baseline --evaluate` scores
  through the ordinary evaluator rather than a second scoring path. See
  [docs/baselines.md](docs/baselines.md).
- **Published canonical baseline scores**, pinned by
  `tests/baselines/fixtures/baseline-scores.json` and regenerated deliberately
  with `scripts/update_baseline_scores.py --confirm --reason ...`. Runtime is
  reported in the documentation rather than pinned, because it is
  machine-dependent.

### Notes (reference baseline agents)

- Baselines are scored as genuine participants: each reads `observed-graph.json`
  and nothing else. The boundary is structural — one module opens one file — and
  is covered by tests that run every agent in a directory from which the ground
  truth has been deleted, that record every path opened during a run, and that
  reject a hard-coded canonical identifier anywhere in the package.
- No schema, generator version or golden digest changed. The baselines are new
  consumers of existing artefacts; they generate nothing.
- Two rules, `GOV-STALE-REVIEW` and `LIF-STALE-ASSET`, are documented as
  under-specified from observed metadata alone. No registry change was made.
- The baselines are **not** production-quality governance agents, and no LLM
  provider integration ships in this milestone.

### Known limitations at 0.1.0

Superseding the `0.1.0rc1` list below, which is kept as written at the time:

- The canonical scenario is deliberately small (180 catalogue assets, ~1 800
  lineage edges): a correctness benchmark, not a load test.
- One estate shape and one defect taxonomy. All four difficulty tiers ship, but
  the adversarial set is a focused initial six case classes over a small
  constructed universe (19 scored pairs at the demo profile), with single-field,
  asset-level near misses only.
- The published baselines are metadata-only and deliberately simple; none opens a
  materialized scientific file, and no LLM-backed agent ships.
- No run-to-run comparison or regression reporting.
- DataHub export is offline file emission only; no live ingestion, no round-trip
  validation, no other catalogue.
- Scores are comparable only within one generator version, config fingerprint,
  profile and seed.
- **Not published to PyPI.** Distribution is by GitHub Release and by building a
  wheel from a checkout.

### Reproducibility at 0.1.0

The golden digests are unchanged from the adversarial-scenario regeneration
recorded above; no canonical bytes moved in preparing this release.

## [0.1.0rc1] — 2026-08-03

First release candidate. The end-to-end benchmark workflow is complete: generate
a synthetic data estate, derive a defective observed view of it with a published
answer key, score a submission against it, package the result as a portable
bundle, and export it as catalogue metadata — all deterministic and offline.

This is the first version intended for people other than the author, so the
entry below describes the whole surface rather than a delta.

### Added — benchmark generation

- **Canonical company model.** A fictional oncology company — programmes,
  studies, teams, people, ownership, stewardship and eight controlled
  vocabularies — authored as versioned YAML under `config/` and validated by
  typed Pydantic models. `dataswamp validate-config`.
- **Deterministic truth graph.** The complete, correct synthetic scientific and
  governance state generated from that model: subjects, biospecimens, assays,
  instrument and pipeline runs, files, datasets, data products, contracts,
  quality checks, governance records, intended-use records, training approvals
  and lineage. Emitted as canonical JSONL shards with a per-shard-digest
  manifest. `dataswamp generate-truth` / `validate-truth`.
- **Scientific file estate.** Small but genuinely readable files for the truth
  graph's assets — H5AD, Parquet, OME-TIFF, PNG, VCF, BED, GeoJSON, Matrix
  Market, FASTQ, CSV/TSV/JSON/JSONL/YAML, gzip — with explicitly declared
  placeholders and sidecars for heavy binaries (BAM, CRAM, DICOM, SVS, Zarr).
  Three profiles (`tiny`, `demo`, `stress`), path-safe and budget-capped writes.
  `dataswamp generate-files` / `validate-files`.

### Added — the observed state and its answer key

- **Imperfection engine.** A deliberately imperfect observed state derived from
  the truth graph by injecting defects from an in-code registry of **41 rules
  across 12 categories**, under six maturity profiles (`gold`, `mostly-good`,
  `typical`, `poor`, `catastrophic`, `demo`). It reads the truth graph from
  disk, checksums it, and verifies it is unmodified; it mutates only JSON copies
  and never the truth entities. `dataswamp inject-defects` / `validate-observed`.
- **Machine-readable ledgers.** Every injected defect is recorded with its
  before/after values, its expected finding, and its expected remediation —
  including the approval policy, approver role and whether the fix is automatic,
  manual or unavailable.
- **Control partition.** `controls.jsonl` names every asset and file left clean,
  with a strict reserved partition held out of every rule's eligible population
  before selection, so true negatives and precision are measurable and a
  flag-everything strategy is visibly penalised. Emitted and independently
  re-validated.
- **Rule and remediation contracts.** `rule-scope.jsonl` publishes each rule's
  population, eligible set, control exclusions and selected set, so a rule's
  denominator is its declared population rather than the whole estate.
  `dataswamp list-defects` / `validate-defects`.

### Added — evaluation

- **Versioned prediction contract** (`schema_version: 1`) with a total
  validator. Three expressible claims — `finding`, `clean` and `abstain` — so an
  abstention is recorded and reported rather than folded into a confusion-matrix
  cell it did not earn. It asks only for what an agent could know from the
  observed graph.
- **Deterministic scorer.** `dataswamp evaluate` produces confusion-matrix and
  remediation reports, byte-identical for identical inputs. Scoring is
  pair-level on `(entity_id, rule_id)`; a prediction against an entity outside a
  rule's population is reported as an out-of-scope false positive rather than
  widening that rule's denominator.
- **Five separate dimensions** — finding detection, control preservation,
  remediation correctness, approval reasoning and non-remediation correctness —
  reported separately, with no weights and no composite score. Undefined metrics
  are emitted as `null` alongside their numerator and denominator, never as
  `0.0`.
- Read-only with respect to every other layer: it consumes emitted artefacts and
  never regenerates or rewrites ground truth.

### Added — distribution

- **Versioned benchmark bundles.** `dataswamp build-bundle` packages emitted
  layers into one portable, self-describing directory: a versioned manifest
  declaring every content file, SHA-256 checksums covering the manifest in turn,
  environment provenance, and licensing and schema notices. Truth-only,
  truth+estate, with-observed and complete-with-evaluation bundles are all
  first-class. A bundle is a directory rather than an archive, deliberately, to
  avoid archive-header nondeterminism.
- **Total verification.** `dataswamp verify-bundle` checks the manifest,
  structure, provenance and every checksum by exact recomputation, reporting
  every failure with the file and the invariant it broke. Nothing is written.
- **Stable streaming reader.** `BundleReader` verifies then streams; no layer is
  ever loaded whole into memory.

### Added — DataHub adapter

- **Offline metadata export.** `dataswamp export-datahub` emits the Metadata
  Change Proposals DataHub's `file` source ingests, plus a ready-to-run recipe
  that reads credentials from environment variables. No server, token or network
  is involved, and **no DataHub package is a dependency** — the adapter emits the
  documented payload shapes directly.
- **Privilege boundary.** `--mode observed` is built from `observed-graph.json`
  *alone* — never the findings, remediations, controls, rule scope or mutation
  log — which is the structural guarantee against truth leakage. `--mode truth`
  is privileged and marked as such in tags, custom properties and the export
  manifest.
- The mapping is pinned by committed fixtures, so a change cannot pass
  unnoticed, and the adapter is the only place in the project a catalogue is
  named.

### Added — release surface (new in this release candidate)

- **`dataswamp demo`** — the whole workflow into one directory: generate, score,
  bundle, verify and export, in a couple of seconds, with no seed, credential or
  network. Byte-identical across runs.
- **Example submissions** under `examples/predictions/` — `perfect`, `partial`
  and `unsafe` — with documented scores for each, plus a Python API example.
- **Packaged configuration and examples.** The canonical `config/` tree and the
  example submissions now ship *inside* the distribution, so an installed
  package can generate a benchmark without a source checkout.
- **Documentation for first contact**: a rewritten README, `docs/public-api.md`
  (stable / experimental / internal / unsupported), `docs/release-checklist.md`,
  `docs/roadmap.md`, `CONTRIBUTING.md`, `SECURITY.md` and this changelog.

### Reproducibility

- Same config, generator version and seed produce byte-identical output.
- Across the whole declared dependency range, the truth graph and the
  observed-state ledgers are byte-identical. The materialized estate is
  byte-identical only within one **environment fingerprint**, because its binary
  payloads are written by pyarrow, Pillow, tifffile and anndata. The claim is
  made per-artefact rather than globally.
- Provenance carries no wall-clock value, hostname, username or path.
- The contract is pinned by committed golden digests, verified in CI on Python
  3.12 and 3.13 against both the locked and the lowest-direct dependency
  resolutions. **The golden digests are unchanged in this release candidate.**

### Known limitations

- The canonical scenario is deliberately small (180 catalogue assets, ~1 800
  lineage edges): a correctness benchmark, not a load test.
- One estate shape and one defect taxonomy — no difficulty tiers, adversarial
  scenarios, cross-asset defects or near-miss controls yet.
- No reference baseline agents are published, so there is no established score
  to compare against.
- No run-to-run comparison or regression reporting.
- DataHub export is offline file emission; live ingestion and round-trip
  validation are not implemented. No other catalogue is supported.
- Scores are comparable only within one generator version, config fingerprint,
  profile and seed.
- **The licence for generated benchmark data is not yet designated.** *(As of
  0.1.0rc1. Superseded after this release: generated benchmark data is now
  CC BY-NC 4.0 — see
  [ADR 0004](docs/adr/0004-generated-data-licensing.md).)*
