# ADR 0007: Catalogue adapters emit documented payloads rather than depending on a client

- **Status:** Accepted
- **Date:** 2026-08-09

## Context

[ADR 0005](0005-direct-rest-datahub-client.md) decided, for DataHub specifically,
to talk REST from the standard library rather than take `acryl-datahub` as a
dependency. It was argued from that one integration, and it named the cost:
payloads are validated against this adapter's own contract rather than upstream's
schemas.

A second catalogue adapter now exists. OpenMetadata ships an official Python
package, `openmetadata-ingestion`, and the same question arrived again — this time
with a different shape, which is what makes it worth generalising rather than
repeating.

Three facts emerged from building the OpenMetadata adapter offline.

**The dependency is disproportionate to the need.**
`openmetadata-ingestion` exists to run ingestion *workflows*: connectors, source
plugins, an Airflow-adjacent runtime, and a generated Pydantic model tree covering
every entity OpenMetadata knows. This adapter creates ten entity kinds and writes
files. Taking the package would add a large, fast-moving tree to a benchmark whose
whole value proposition is that its output is byte-reproducible.

**The schemas are available without the client.** OpenMetadata publishes its JSON
schemas in `openmetadata-spec`, under Apache-2.0. A 21-file subset — the ten
`Create<Entity>` requests plus the shared types they reference — is enough to
validate every payload this adapter emits, including `additionalProperties: false`
and every enum. That is *stronger* validation than ADR 0005 could get for DataHub,
and it costs a test fixture rather than a runtime dependency. ADR 0005's stated
cost is therefore partly bought back here.

**A generated client would not have caught the interesting bugs anyway.** The two
real defects found while building this adapter were an ordering bug (data-product
asset attachments interleaving with data products) and a modelling question
(OpenMetadata's `TestDefinition.entityType` admitting only `TABLE`/`COLUMN`).
Neither is a serialisation problem, which is the only class an SDK would have
prevented.

## Decision

**The current policy for DataSwamp catalogue adapters is: emit documented payload
shapes, validate them offline against upstream's own schemas where those are
published, and take no catalogue-client runtime dependency.**

Concretely:

- No catalogue client — `acryl-datahub`, `openmetadata-ingestion`, or a successor
  — appears in `[project].dependencies`.
- No HTTP client library appears there either. A live path, where one exists,
  uses the standard library with every endpoint confined to one module.
- Where upstream publishes machine-readable schemas, a **minimum reachable
  subset** is vendored under a test-scoped directory with recorded provenance, and
  emitted payloads are validated against it offline.
- Schema-validation tooling (`jsonschema`) is a **dev** dependency. Installing
  DataSwamp must never install anything catalogue-shaped.
- `tests/adapters/test_isolation.py` enforces all of the above.

## What this decision is *not*

It is **not** a universal or irreversible law. It is the policy that fits the two
integrations built so far, and it is grounded in a specific pair of conditions:
the payload surface is small, and upstream publishes enough of its contract to be
validated against independently.

A future catalogue could fail either condition. If a platform's API is only
honestly reachable through an official SDK — because authentication is
non-trivial, because the wire format is undocumented or unstable, or because the
protocol carries semantics no published schema expresses — then integrating it
responsibly *through that SDK* is the better engineering decision, and this ADR
should be superseded rather than worked around. Emitting a payload shape nobody
can check is not a virtue; it is the failure mode this policy exists to avoid, in
a different costume.

The test to apply is not "does it add a dependency" but **"can the integration's
correctness be demonstrated without one?"** For DataHub and OpenMetadata, it can.

## Rationale

**A benchmark's dependency set is part of its output.** Byte-determinism is
guaranteed against a committed lockfile, and `provenance.json` fingerprints the
direct dependency versions because they determine the generated bytes. Every
dependency added is one more thing whose upgrade can move a published score. A
catalogue client — installed by everyone, used by one adapter — is a poor trade.

**Adapters must stay adapters.** ADR 0001 and ADR 0002 fix the dependency
direction: the core layers know nothing about any catalogue, and an adapter
consumes their emitted artefacts. A runtime client tends to pull its types
inward — a convenience import here, a shared model there — and the boundary
erodes by increments rather than by decision.

**Offline provability is the point.** The whole OpenMetadata adapter is testable
with no server, no network, no credentials and no Docker. That is what makes it
reviewable in a pull request and runnable in a fork. ADR 0006's separation of
*declared target* from *tested point* only means something if the untested part is
still checkable against something real — which is exactly what the vendored
schemas provide.

**The narrow subset is a feature.** Vendoring twenty-one files invites review;
vendoring the tree does not. An unresolvable `$ref` when a new field starts being
emitted is a useful alarm, and it only stays useful while the subset is small.

## What this trades away

**Upstream model changes are found by us, not announced to us.** A client library
would break loudly on `pip install`. Here, a changed `required` list is found when
someone deliberately refreshes the vendored schemas, or when a live canary goes
red. The mitigations are ADR 0006's policy and, per catalogue, a canary — which
for OpenMetadata does not exist yet, and which is why
`VERIFIED_OPENMETADATA_VERSION` is `None`.

**Some transport work is reimplemented per catalogue.** DataHub's live client is
~470 lines of standard-library REST. An OpenMetadata one would be comparable.
That is the price, and it is bounded because each stays confined to one module.

**No shared adapter layer exists yet.** The two adapters duplicate an id-escaping
codec and an atomic-directory writer. That duplication is deliberate for now: with
exactly two examples it is not yet clear which similarities are structural and
which are coincidental, and a premature `adapters/common/` would have to be undone
the first time two catalogues' rules genuinely diverge. Revisit when a third
adapter exists, or when the two are known to have stopped diverging.

## Consequences

- `tests/adapters/test_isolation.py` asserts no catalogue or HTTP client is a
  runtime dependency, that the two adapters do not import each other, that no
  `adapters/common/` exists, and that the OpenMetadata adapter opens no socket.
- The vendored OpenMetadata schema subset is documented in
  `tests/adapters/openmetadata/schemas/PROVENANCE.md` and refreshed only by
  `scripts/update_openmetadata_fixtures.py --schemas --confirm --reason ...`.
- Superseding this ADR is the expected route for a catalogue that genuinely needs
  an SDK. Adding one quietly is not.
